Étape 0 : Prise de Décision

La Réflexion Pré-Projet : Comment Choisir ?

On ne commence jamais un projet en choisissant aveuglément des outils. Une architecture data découle de compromis précis entre 4 contraintes majeures.

1. La Volumétrie

Mo à quelques Go : Un PostgreSQL suffit largement.
Centaines de Go à Pétaoctets : Nécessite un stockage objet distribué (MinIO/S3) et un moteur distribué (Spark).

2. La Variété

Structurée (tables SQL) ➔ Data Warehouse direct.
Semi-structurée (JSON, logs) ou non-structurée (images, audio) ➔ Data Lake obligatoire pour réceptionner le format natif.

3. La Vélocité

Batch (quotidien / horaire) ➔ Pipelines PySpark programmés.
Temps réel / Streaming ➔ Kafka, Spark Structured Streaming avec ingestion continue dans la couche Bronze.

4. L'Usage Final

BI & Dashboards rapides ➔ Couche Gold relationnelle / Data Marts.
Machine Learning & Data Science ➔ Accès direct aux fichiers Parquet propres de la couche Silver.

Les Piliers du Stockage

Data Lake, Data Warehouse ou Data Mart ?

Ces trois concepts ne s'opposent pas : ils s'emboîtent au sein d'une chaîne de valeur analytique cohérente.

Data Lake Stockage Objet

Le Lac de Données

Dépôt centralisé stockant toutes les données brutes dans leur format natif, à coût de stockage minimal et avec une scalabilité infinie.

  • Schéma à la lecture (Schema-on-Read)
  • Tous formats : Parquet, JSON, CSV, logs, images
  • Risque de "Data Swamp" sans gouvernance
Exemples : MinIO, AWS S3, Azure Data Lake (ADLS), Google Cloud Storage.
Data Warehouse Base Analytique

L'Entrepôt de Données

Base de données hautement modélisée, optimisée pour exécuter des requêtes SQL complexes et croiser des données historiques d'entreprise.

  • Schéma à l'écriture (Schema-on-Write strict)
  • Performances SQL de pointe via indexation
  • Données 100% nettoyées et unifiées
Exemples : PostgreSQL (Gold local), Snowflake, Google BigQuery, AWS Redshift.
Data Mart Sous-ensemble Métier

Le Magasin de Données

Sous-ensemble du Data Warehouse taillé sur mesure pour un département spécifique (ex: Finance, Marketing, Logistique de taxis).

  • Ultra-ciblé sur un besoin business
  • Accès simplifié pour les analystes et Metabase
  • Temps de réponse instantané (< 50 ms)
Dans notre TP : Tables agg_daily_taxi_metrics, agg_hourly_demand.
Concepts Fondamentaux

OLTP vs OLAP et ETL vs ELT

Comprendre la différence entre exécuter une application transactionnelle et analyser des millions de données historiques.

Le Duel : OLTP vs OLAP

Indispensable en entretien Data
Caractéristique OLTP (Online Transaction Processing) OLAP (Online Analytical Processing)
Objectif Principal Faire tourner les opérations quotidiennes de l'application (ex: réserver une course de taxi). Aider les dirigeants et analystes à prendre des décisions stratégiques (KPIs, tendances).
Type d'opérations Écritures & Mises à jour rapides unitaires : INSERT, UPDATE, DELETE. Lectures massives avec calculs d'agrégation : SELECT SUM(), AVG(), GROUP BY.
Volumétrie touchée Quelques lignes à chaque requête (accès par clé primaire). Des millions à des milliards de lignes scannées à la fois.
Modélisation Normalisée (3NF) pour éliminer toute redondance et garantir l'intégrité ACID. Dénormalisée (Schéma en étoile / flocon) pour minimiser les jointures coûteuses.
Stockage typique Ligne par ligne (Row-oriented). Colonnaire (Parquet, ClickHouse, Snowflake).
Approche Classique

ETL (Extract ➔ Transform ➔ Load)

Les données sont extraites, transformées sur un serveur intermédiaire dédié (ex: Talend, Informatica), puis seulement les données finales nettoyées sont insérées dans la base.

⚠️ Inconvénient majeur : Les données brutes d'origine sont perdues. Si la règle de calcul change, impossible de rejouer le passé !
Approche Moderne (Notre Projet)

ELT (Extract ➔ Load ➔ Transform)

Les données sont extraites et immédiatement chargées brutes dans le Data Lake (Bronze). Ensuite, la puissance distribuée (Apache Spark, SQL) est exploitée pour transformer à volonté.

✅ Avantage décisif : Rejouabilité totale, flexibilité absolue pour la Data Science et le reporting.
Le Roi du Big Data

Pourquoi Apache Parquet a Remplacé le CSV ?

Parquet est un format de fichier binaire, colonnaire et compressé, conçu pour maximiser les performances de requêtage en Big Data.

Format Ligne (CSV, PostgreSQL standard)

Pour calculer le chiffre d'affaires moyen (colonne fare_amount), le disque doit lire toutes les colonnes de chaque ligne (date, id, adresses, drapeaux...).

// Lecture disque séquentielle :
Ligne 1: [ID_1, 2024-01-01, 14.50, Manhattan, Visa, 1]
Ligne 2: [ID_2, 2024-01-01, 28.00, Queens, Cash, 2]
➔ 100% du fichier chargé en mémoire RAM.
Format Colonnaire (Apache Parquet)

Les valeurs d'une même colonne sont stockées contiguës sur le disque. Le moteur de calcul ignore totalement les colonnes non demandées !

// Lecture ciblée uniquement sur la colonne ciblée :
[ID_1, ID_2, ID_3...] ➔ Ignoré
[14.50, 28.00, 9.20...] ➔ Seule colonne lue !
[Manhattan, Queens, Brooklyn...] ➔ Ignoré
➔ 80% d'I/O disque et de mémoire économisés.

1. Taux de Compression Élevé

Comme une colonne ne contient qu'un seul type de données (ex: tous des flottants), les algorithmes (Snappy, GZIP, Run-Length Encoding) compressent 5 à 10 fois mieux qu'en CSV.

2. Predicate Pushdown

Chaque groupe de lignes (Row Group) enregistre les valeurs Min et Max. Pour WHERE fare > 50, Spark saute les blocs où Max = 30 sans même les lire !

3. Projection Pushdown

Si votre table comporte 80 colonnes mais que votre requête n'en demande que 2, seules les 2 colonnes sont chargées depuis le disque ou le bucket S3.

Le Cœur du Projet

L'Architecture Médaillon : Bronze ➔ Silver ➔ Gold

Chaque couche applique un contrat de service précis et prépare les données pour une audience différente.

1

Couche Bronze (Raw Landing Zone)

MinIO / s3a://bronze/

La couche Bronze est la porte d'entrée de votre plateforme de données. Elle réceptionne les flux bruts tels qu'émis par les sources (AWS Open Data, API, Kafka, bases opérationnelles).

Règles d'or absolues :
  • • Immutabilité totale : on ne modifie JAMAIS les données brutes.
  • • Pas de filtrage : même les prix négatifs et erreurs sont conservés !
  • • Auditabilité : traçabilité de l'origine et timestamp d'ingestion.
Dans notre projet TP :

Téléchargement du Parquet NYC TLC (~3M courses) et CSV des zones ➔ MinIO bucket bronze dans nyc_taxi/raw_year=2024/raw_month=01/.

2

Couche Silver (Cleaned & Conformed)

MinIO / s3a://silver/

La couche de vérité d'entreprise (Single Source of Truth). PySpark nettoie, type rigoureusement, filtre les anomalies, enrichit et partitionne les données.

Transformations PySpark réalisées :
  • • Filtrage : élimination des tarifs négatifs, distances nulles, passagers = 0.
  • • Feature Engineering : calcul de la durée (minutes), vitesse moyenne (mph), taux de pourboire.
  • • Jointure : enrichissement géographique avec les Boroughs (Manhattan, Queens...).
Optimisation physique :

Format Parquet Snappy partitionné par date (pickup_date=YYYY-MM-DD). Idéal pour les Data Scientists et requêtes d'entraînement de modèles ML.

3

Couche Gold (Curated Business & Data Marts)

PostgreSQL (gold_db)

La couche orientée métier. On ne stocke plus des trajets individuels bruts, mais des indicateurs agrégés prêts à être consommés directement par les décideurs via des outils de BI comme Metabase.

Pourquoi PostgreSQL et pas le Data Lake ?
  • • Latence sub-seconde pour les tableaux de bord interactifs.
  • • Indexation B-Tree sur les colonnes clés (date, borough).
  • • Concurrence d'accès élevée pour des dizaines d'utilisateurs simultanés.
Data Marts créés dans le TP :

• agg_daily_taxi_metrics : CA, courses et pourboires quotidiens.
• agg_hourly_demand : heures de pointe et vitesse du trafic.
• agg_borough_flows : flux Origine ➔ Destination.
